# InsCheck — [А14] ON-LINE проверка полисов

Перенос SOAP-сервиса `GetInsPrkState` со старого стека (ASP.NET/VB + Oracle) на
новый (Java Spring Boot + PostgreSQL).

**Главное требование сохранено:** входные и выходные данные и их формат полностью
идентичны старому сервису (namespace `http://tempuri.org/`, теги `query`/`answer`),
поэтому существующие клиенты работают без изменений.

## Стек

- Java 21, Spring Boot 3.3, Spring Web Services (SOAP, contract-first по XSD)
- PostgreSQL (доступ через `NamedParameterJdbcTemplate`, SQL — в отдельных файлах)

## Архитектура (три слоя, в разных файлах — по правилам постановки)

| Слой        | Класс/пакет                              | Назначение                                  |
|-------------|------------------------------------------|---------------------------------------------|
| Контроллер  | `ws/InsCheckEndpoint`                     | SOAP-эндпоинт, приём запроса, сетевой контекст |
| Сервис      | `service/InsCheckService`, `InputValidator` | бизнес-логика (разделы 2–6 постановки)      |
| DAO         | `dao/InsCheckDao`, `InsCheckLogDao`, `InsCheckLimitDao` | **весь** доступ к БД                |

SQL вынесен в `src/main/resources/sql/**` (загрузка — `util/SqlLoader`).

## Что реализовано (по постановке)

1. SOAP-метод `GetInsPrkState` с идентичным контрактом.
2. Проверка входных данных — Таблица 4 (коды 2,3,4,5,100–111).
3. Журнал операций `INSCHECKLOG` (раздел 3.1) и счётчик лимитов `INSCHECKLIMIT` (3.2).
4. Поиск СП по алгоритмам Таблицы 1: разделы **С** (С01–С03), **Р** (Р01), **В** (В01–В06)
   и **новый этап H** (H01–H03) — вставлен между Р и В (см. задание).
5. Выбор СК* (по `IDMain`) и ПЗСК* (раздел 4.5), прикрепление (раздел 5).
6. Формирование ответа: `ack`, `err[]`, `alg[]`, `ins`, `prk[]`, `p_disp/p_proph/p_healthc`.

### Алгоритмы «схожести» и «метафона»

В старой системе логика жила в Oracle-пакете `inscheck.GetAnswer`, которого нет в
исходниках. Восстановлено по постановке:

- **«схожее» (≥0.8)** — `similarity()` (расширение `pg_trgm`).
- **«метафон/созвучное»** — сравнение с предрасчитанными колонками `META_FAM/META_IM/
  META_OT` (на них ссылается постановка). Метафон входного значения считается в Java
  (`util/RussianMetaphone`).

Места, требующие сверки с генератором регистра РС ЕРЗ или уточнения данных, помечены
комментариями `TODO` (метафон, межзаписный поиск в пределах СК, источник признаков
диспансеризации).

## Запуск

```bash
# 1. Поднять PostgreSQL и накатить схему
psql -U inscheck -d inscheck -f src/main/resources/db/schema.sql

# 2. Собрать и запустить (параметры БД — через переменные окружения)
DB_URL=jdbc:postgresql://localhost:5432/inscheck DB_USER=inscheck DB_PASSWORD=inscheck \
  mvn spring-boot:run
```

- WSDL: `http://localhost:8080/ws/inscheck.wsdl`
- Эндпоинт SOAP: `http://localhost:8080/ws`

## Проверено локально (end-to-end)

- Успех: `ack=0`, заполнены `alg`, `ins`, `prk`, признаки — формат совпадает с примером
  из постановки (п.3.1.6).
- Ошибки: `ack=2`, коды 108+200 и т.п.; запись в журнал, инкремент счётчика лимитов.
- Новый этап **H01** срабатывает, когда разделы С/Р не дали результата.
